# 一、技术难点

## 1. 游戏状态同步与信息不对称

爆炸猫是**完全信息不对称**游戏——每位玩家只能看到自己的手牌，牌库顺序对所有玩家不可见（除非使用偷看牌），弃牌堆公开。服务器必须作为**权威状态源**，客户端只渲染自己能看的信息。牌库是有序队列（偷看、洗牌、放回爆炸猫都会改变顺序），不能简单随机抽牌。   

## 2. Nope 链的时序处理  

Nope 可以打断任何行动，且 Nope 本身又能被 Nope，形成嵌套链。需要设计**动作栈（Action Stack）**机制：

- 玩家 A 出三张猫牌 → 请求：要 B 的拆解
- 玩家 B 出 Nope → 入栈顶
- 玩家 A 出 Nope → 入栈顶
- 结算：栈顶 Nope 生效 → 三张猫牌效果恢复 → B 给牌

每个动作都需要**等待窗口期**让其他玩家有机会出 Nope，超时后自动结算。

## 3. 攻击叠加的抽牌计数

攻击牌让下家抽 N 张牌，下家打出攻击牌又传给下家，N 累加。需要维护一个**待抽牌计数器**，每回合递减，并在回合流转中正确传递。

## 4. 回合与行动队列

攻击牌改变回合顺序（跳过被攻击者），需要设计**灵活的回合调度器**，而非简单的轮转。转向、三张猫牌等需要选择目标玩家的操作，需要等待玩家响应。

## 5. 防作弊与安全

所有牌面逻辑必须在服务端验证，客户端只做展示。客户端不能知道牌库顺序、对手手牌、未翻开的牌。必须防止篡改请求（如伪造手牌、假装有拆解）。

## 6. 断线重连与超时

有人掉线不能无限等待，需要**超时机制**（如 60 秒无操作自动跳过/出牌）。断线重连后要恢复玩家的手牌视图，但牌库信息不能泄露给其他玩家。

## 7. 组合技合法性校验

服务端必须验证：确实是 3 张相同猫牌、目标玩家确实有指定牌、五张不同猫牌确实互不相同等。

# 二、技术栈

## 后端

| 技术 | 具体方案 | 理由 |
|-|-|-|
| 语言 | Go | 高性能并发，goroutine 天然适合 WebSocket 长连接管理；单二进制部署 |

| 数据库 | PostgreSQL | 用户信息、游戏历史记录、排行榜 |

## 前端

| 技术 | 具体方案 | 理由 |
|-|-|-|

# 三、模块划分与职责

## 后端模块（Go）

### server/ — 应用入口层

- **main.go**：程序启动入口，初始化所有模块
- **config.go**：配置管理（端口、Redis 连接、超时时间等）
- **routes.go**：HTTP 路由和 WebSocket 升级处理

### room/ — 房间管理

- **Room**：房间实体，包含房间 ID、玩家列表、游戏状态、设置项
- **RoomManager**：房间池，创建/加入/退出/解散房间
- **RoomLifecycle**：房间状态机，等待中→游戏中→已结束

### game/ — 核心游戏逻辑（纯函数，无 I/O）

- **Deck**：牌库引擎，洗牌、抽牌、插牌、偷看牌顶、切牌
- **Card**：卡牌类型定义，类型枚举、效果定义、组合规则
- **Hand**：手牌操作，出牌、弃牌、抢牌、合法性校验
- **TurnEngine**：回合调度器，当前玩家、下家、攻击叠加抽牌数   
- **ActionStack**：动作栈，Nope 链核心实现，支持嵌套撤销
- **MoveValidator**：合法性校验，检查出牌时机、目标、组合条件
- **GameOver**：胜负判定，检查是否只剩一人

### session/ — 玩家与会话状态

- **PlayerState**：单个玩家状态（手牌、存活、拆解数、连接状态）
- **GameState**：全局游戏状态（牌库、弃牌堆、当前回合、动作栈）
- **StateSerializer**：状态序列化，按玩家视角过滤可见信息

### network/ — 网络通信

- **GameSocket**：WebSocket 连接管理，封装读写
- **EventHandler**：事件分发，客户端消息→路由到游戏逻辑
- **Broadcaster**：广播，向全员/单人/部分玩家发送状态更新

### timer/ — 超时控制

- **TurnTimer**：回合超时，60 秒无操作自动跳过/出牌
- **NopeTimer**：Nope 等待窗口，3 秒无人出 Nope 则自动结算
- **ReconnectTimer**：断线重连倒计时，掉线后 90 秒等待

### persistence/ — 持久化

- **RedisAdapter**：Redis 读写，缓存游戏状态
- **Database**：PostgreSQL 操作，用户信息、战绩、历史记录

### types/ — 共享类型定义

- 卡牌类型枚举、事件类型枚举、游戏阶段枚举、所有 DTO 定义

## 前端模块（React + TypeScript）

### pages/ — 页面级组件

- **HomePage**：首页，创建/加入房间、设置昵称
- **RoomPage**：房间等待页，玩家列表、准备状态
- **GamePage**：游戏主页面，牌桌视图
- **ResultPage**：结算页，胜负结果、再来一局

### components/Card/ — 卡牌相关

- **CardView**：单张卡牌渲染（正面/背面）
- **HandArea**：手牌区，扇形排列，可选中
- **DeckView**：牌库视图，显示背面，偷看后显示牌顶
- **DiscardPile**：弃牌堆

### components/Board/ — 牌桌布局

- **GameBoard**：牌桌整体布局
- **PlayerAvatar**：玩家头像，存活/出局状态标识
- **TurnIndicator**：当前回合指示器
- **OpponentHand**：对手手牌，仅显示背面张数

### components/Actions/ — 操作面板

- **ActionPanel**：可执行的操作按钮列表
- **NopePrompt**：Nope 弹窗，是否出 Nope，倒计时
- **CardSelector**：选牌弹窗，转向/三张猫牌时选目标牌
- **TargetSelector**：选目标玩家弹窗       

### hooks/ — 自定义 Hooks

- **useSocket**：WebSocket 连接管理

### services/ — 网络层

- **socket**：WebSocket 客户端实例
- **eventEmitter**：事件注册/解绑封装

### store/ — 状态管理

# 四、后端模块技术设计

## 4.1 信息存储方案

爆炸猫是高频实时交互游戏，每张牌的操作都会改变状态。不推荐将游戏中的状态直接存储在数据库中，因为每次操作都需要完整的 DB 读写往返，延迟过高。推荐采用**三层存储架构**：

### 第1层：内存（Primary）

游戏进行中的**所有状态只存在于内存**，用 Go 的普通 struct 表示。整个游戏状态只在一个 goroutine 内串行处理（通过 channel 驱动），不需要分布式锁。状态量极小，按 5 人局算，全部序列化仅 2-5 KB，出牌操作是纯内存操作，纳秒级完成。

```go
type GameState struct {
    Deck        []Card              // 牌库（有序队列）
    DiscardPile []Card              // 弃牌堆
    Hands       map[string][]Card   // 玩家手牌
    Turn        TurnState
    ActionStack []Action
    Status      GameStatus
    Players     []PlayerInfo
}
```

### 第2层：Redis（热备）

内存状态在服务器崩溃时会丢失，用 Redis 做轻量级备份。每次状态变更后异步序列化写入 Redis，不阻塞游戏主流程。设置 TTL（如 24 小时）自动清理已结束/废弃的房间。Redis 是内存的二级镜像，不是主存储，其性能接近内存，提供了跨进程的持久能力。

```bash
SET game_state:room:{room_id} <JSON>
EXPIRE game_state:room:{room_id} 86400
```

### 第3层：PostgreSQL（归档）

只在对局**结束后**写入，不参与游戏进行中的任何路径。用于存储用户信息、战绩、排行榜、历史对局记录（含全量操作日志，可用于回放）。

```sql
CREATE TABLE game_records (
    id           UUID PRIMARY KEY,
    room_id      VARCHAR(32),
    players      JSONB,
    action_log   JSONB,
    result       JSONB,
    created_at   TIMESTAMPTZ,
    finished_at  TIMESTAMPTZ
);
```

### 数据流总览

```text
Client A --+
Client B --+-- WebSocket --> Game Handler --> 纯函数状态机 --> 新状态
Client C --+                                                    |
                                                                +--> 更新内存 (primary)
                                                                +--> 异步 --> Redis (backup)
                                                                +--> 异步 --> 广播给客户端

游戏结束后 --> PostgreSQL (archive)
```

### 数据分布总表

| 数据 | 存储位置 | 原因 |
|-|-|-|
| 游戏中的状态（牌库、手牌、动作栈） | **内存** | 极低延迟，状态量小 |
| 游戏状态备份 | **Redis** | 快速恢复，异步写入不阻塞 |
| 用户账号信息 | **PostgreSQL** | 持久化，不频繁读写 |
| 历史对局记录 | **PostgreSQL** | 游戏结束后写入，离线分析 |
| 排行榜/统计数据 | **PostgreSQL** | 定期计算或离线聚合 |

**核心原则**：游戏进行中的热路径全部走内存，数据库只做持久化和离线查询。

## 4.2 Redis 存储内容

Redis 存储的是**游戏状态的完整快照**，用于服务器崩溃后的恢复。一个房间对应一个 Redis key，value 是整个游戏状态的 JSON 序列化。

具体包含以下四部分：

- **牌库（Deck）**：牌库里的每张牌，按当前顺序一字排开，包含牌面朝下的所有牌和爆炸猫的位置。
- **手牌（Hands）**：每名玩家手里的牌。Redis 存全量（包括敏感信息），因为服务器崩溃后需要完整恢复。
- **弃牌堆（Discard Pile）**：已经打出的牌，按打出顺序排列。
- **回合状态 + 动作栈**：当前轮到谁、方向、待抽牌数、Nope 链上的待处理动作。

值得注意的是，Redis 存的是序列化后的卡牌对象（Card.id + Card.type），不是数据库行记录。卡牌从始至终没有独立的数据库行，它们只在游戏初始化时由 Go 代码构造出来，存在于内存中，以 JSON 形式备份到 Redis。

## 4.3 多玩家交互技术

### 传输层：WebSocket

爆炸猫的所有操作（出牌、Nope、选目标）都是双向高频交互，WebSocket 是唯一合理选择。它提供双向通信和低延迟，浏览器原生支持。

### 并发模型：每房间一个 goroutine + channel

核心模式是**一个房间对应一个 goroutine，所有游戏逻辑串行执行**。每个玩家连接后，把 WebSocket 的读写封装成 channel，注册到房间的 inbox。游戏逻辑 goroutine 只有一个，所有玩家消息通过 channel 汇入，串行处理，不需要任何锁，没有竞态条件。

```go
func (r *Room) Run(ctx context.Context) {
    for {
        select {
        case <-ctx.Done():
            return
        case msg := <-r.inbox:
            r.handleMessage(msg)    // 串行处理所有玩家消息
        case <-r.turnTimer.C:
            r.handleTimeout()
        case <-r.nopeTimer.C:
            r.resolveNopeWindow()
        }
    }
}
```

### 消息协议设计

**客户端 → 服务端（Action）**：

```json
{
  "type": "play_card",
  "payload": {
    "card_ids": ["cat_01", "cat_02", "cat_03"],
    "target_player": "user_002",
    "target_card_type": "defuse"
  }
}
```

**服务端 → 客户端（Event）**：

```json
{
  "type": "state_update",
  "payload": {
    "your_hand": [{"id": "defuse_01", "type": "defuse"}],
    "opponents": [{"id": "user_002", "hand_size": 4, "alive": true}],
    "discard_pile": [{"id": "skip_01", "type": "skip"}],
    "deck_count": 28,
    "current_turn": "user_001",
    "pending_draws": 0,
    "phase": "action",
    "action_stack": [],
    "nope_remaining_ms": 0
  }
}
```

### 广播策略：按视角过滤

服务端收到 Action → 状态机处理 → 产生新状态 → 对每个玩家分别序列化后发送。每个玩家只能看到自己的手牌，对手只显示手牌张数，牌库只显示剩余数量。

```go
func (r *Room) BroadcastState() {
    for playerID, ch := range r.connections {
        view := r.SerializeFor(playerID)
        data, _ := json.Marshal(view)
        ch <- data
    }
}
```

### 断线重连

服务端检测到读错误 → 标记玩家为 disconnected → 启动 ReconnectTimer（90秒）。玩家重新连接时建立新 WebSocket，服务端发送完整当前状态视图（按该玩家视角过滤）。超时未重连则自动弃权/出局。

## 4.4 回合调度器设计

爆炸猫的回合流充满异常跳转，不能使用简单的轮转。核心模型是**环形链表 + 有限状态机**。

### 玩家回合的两个阶段

```text
                    +--------------------------+
                    |                          |
                    v                          |
    +----------+  出牌/Skip/Attack  +----------+
    | Action   | ---------------> | Action   |
    | (出牌阶段) |                   | (同一玩家) |
    +----+-----+                   +----+-----+
         |                              |
         | 选择结束出牌                   | 打出 Attack
         v                              v
    +----------+                  +----------+
    | Drawing  |                  | 轮到下家  |
    | (抽牌阶段) |                  | Drawing  |
    +----+-----+                  +----+-----+
         |                              |
         | pendingDraws == 0            | pendingDraws > 0
         v                              v
    +----------+                  +----------+
    | 轮到下家  |                  | 继续抽牌  |
    | Action   |                  | Drawing  |
    +----------+                  +----------+
```

### 核心数据结构

```go
type TurnEngine struct {
    players      []string  // 存活玩家，按座位顺序
    currentIdx   int       // 当前玩家在 players 中的索引
    direction    int       // 1 = 顺时针, -1 = 逆时针
    pendingDraws int       // 攻击牌累积的待抽牌数
    phase        TurnPhase
}

type TurnPhase int

const (
    PhaseAction     TurnPhase = iota // 出牌阶段
    PhaseDrawing                     // 抽牌阶段
    PhaseNopeWindow                  // Nope 等待窗口
    PhaseGameOver                    // 游戏结束
)
```

### 核心方法

```go
// 获取下一个存活玩家的索引（环形）
func (te *TurnEngine) nextIndex() int {
    next := te.currentIdx + te.direction
    n := len(te.players)
    if next >= n { return 0 }
    if next < 0 { return n - 1 }
    return next
}

// 玩家打出 Skip
func (te *TurnEngine) OnSkip() {
    te.currentIdx = te.nextIndex()
    te.phase = PhaseAction
}

// 玩家打出 Attack
func (te *TurnEngine) OnAttack() {
    te.pendingDraws += 2
    te.currentIdx = te.nextIndex()
    te.phase = PhaseDrawing // 下家直接进入抽牌阶段
}

// 抽了一张牌（非爆炸猫）
func (te *TurnEngine) OnCardDrawn() {
    te.pendingDraws--
    if te.pendingDraws <= 0 {
        te.currentIdx = te.nextIndex()
        te.phase = PhaseAction
    }
}

// 玩家出局
func (te *TurnEngine) RemovePlayer(playerID string) {
    idx := indexOf(te.players, playerID)
    if idx < te.currentIdx { te.currentIdx-- }
    te.players = append(te.players[:idx], te.players[idx+1:]...)
    if len(te.players) == 1 { te.phase = PhaseGameOver }
}
```

**核心设计**：pendingDraws 作为债务在整个回合系统中流转。打 Attack 则债务 +2 并转给下家，不打出 Attack 则自己还债（抽牌），还完债轮到下家。

## 4.5 游戏状态机

游戏状态机把一局游戏的**整个生命周期**拆成若干个明确的状态，并且规定清楚在哪个状态能做什么事，做完后进入哪个状态。

### 生命周期状态

```text
         +--------------+
         |   Waiting    |  <- 等人齐，准备阶段
         +------+-------+
                | 所有人点准备
                v
         +--------------+
         |   Dealing    |  <- 发牌阶段（发拆解、普通牌，插爆炸猫）
         +------+-------+
                | 发牌完成
                v
    +---------------------------+
    |       Playing             |  <- 游戏进行中
    |  +--------------------+   |
    |  |  Action Phase      |   |  <- 出牌阶段，可以出牌/结束
    |  +--------+-----------+   |
    |           | 选择抽牌       |
    |           v               |
    |  +--------------------+   |
    |  |  Drawing Phase     |   |  <- 抽牌阶段，必须抽牌
    |  +--------+-----------+   |
    |           | 抽到牌         |
    |  +--------+-----------+   |
    |  |  Nope Window       |   |  <- 等待3秒，看是否有人出 Nope
    |  +--------+-----------+   |
    |           | 超时或结算完毕  |
    |           v               |
    |  +--------------------+   |
    |  | 回到 Action/Draw   |   |  <- 继续游戏
    |  +--------------------+   |
    +----------+----------------+
               | 只剩一人存活
               v
         +--------------+
         |   GameOver   |  <- 游戏结束
         +--------------+
```

### 状态与操作的约束关系

| 操作 | Waiting | Dealing | Playing | GameOver |
|-|-|-|-|-|
| 出牌 | 禁止 | 禁止 | 允许 | 禁止 |
| 抽牌 | 禁止 | 禁止 | 允许 | 禁止 |
| 准备 | 允许 | 禁止 | 禁止 | 禁止 |
| 出 Nope | 禁止 | 禁止 | 允许\* | 禁止 |

### 状态机 vs 回合调度器

| 层次 | 负责 | 例子 |
|-|-|-|
| **游戏状态机** | 整局游戏的宏观生命周期 | 等待→发牌→游戏→结束 |
| **回合调度器** | 游戏进行中的微观轮转 | 谁出牌、下一步谁、欠几张牌 |

状态机管"游戏进行到什么大阶段了"，回合调度器管"游戏进行中，具体轮到谁了"。

## 4.6 Nope 链设计

Nope 链是爆炸猫**最复杂的机制**。核心难点不在于栈本身，而在于 Nope 窗口的计时重置和多玩家同时出 Nope 的裁决。

### Nope 链的本质：奇偶抵消

从栈底往上遍历，Nope 每出现一次就翻转一次生效状态：

```text
A 出三张猫牌 --> Nope(B) --> Nope(A) --> Nope(C)
                                         |
                              栈顶 Nope 生效，C 的 Nope 抵消了 A 的 Nope
                              最终结果：三张猫牌被 B 的 Nope 抵消

数学上：从栈底向上遍历，Nope 每出现一次翻转一次生效状态
初始: 三张猫牌 = 生效
遇到 Nope(B) --> 翻转 --> 不生效
遇到 Nope(A) --> 翻转 --> 生效
遇到 Nope(C) --> 翻转 --> 不生效（最终结果）
```

### 动作栈数据结构

```go
type ActionStack struct {
    stack []StackEntry
    timer *time.Timer
}

type StackEntry struct {
    Action     Action   // 原始动作
    Actor      string   // 发起者
    Noped      bool     // 是否被 Nope（结算时计算）
}

type ActionType int

const (
    ActionPlayCard   ActionType = iota // 出牌
    ActionNope                         // 出 Nope
    ActionDraw                         // 抽牌
)
```

### Nope 窗口的时序管理

Nope 窗口需要满足：每次有人出牌 → 开启 3 秒窗口；有人出了 Nope → 重置窗口，再等 3 秒；3 秒内无人出 Nope → 自动结算。

```go
// 开启 Nope 窗口
func (g *GameLoop) openNopeWindow(duration time.Duration) {
    if g.nopeTimer != nil { g.nopeTimer.Stop() }
    g.nopeTimer = time.NewTimer(duration)
    g.state.Turn.Phase = PhaseNopeWindow
    g.broadcastNopePrompt(duration)
}

// 有人出 Nope
func (g *GameLoop) handleNope(playerID string) {
    g.state.ActionStack.Push(StackEntry{
        Action: Action{Type: ActionNope},
        Actor:  playerID,
    })
    g.openNopeWindow(3 * time.Second)  // 重置窗口
    g.broadcastNopePlayed(playerID)
}

// 结算（奇偶抵消）
func (s *ActionStack) Resolve() ResolveResult {
    baseAction := s.stack[0]
    nopeCount := 0
    for i := 1; i < len(s.stack); i++ {
        if s.stack[i].Action.Type == ActionNope {
            nopeCount++
        }
    }
    return ResolveResult{
        Action:        baseAction,
        ActionBlocked: nopeCount%2 == 1,
        NopeCount:     nopeCount,
    }
}
```

### 竞态处理

Nope 窗口关闭的瞬间，可能有玩家恰好在同一时刻出了 Nope。Go 的 select 对多个就绪的 case 是随机选择，所以不能直接依赖 timer.C 触发就结算。需要在结算前先 drain 掉 inbox 中积压的消息：

```go
func (g *GameLoop) resolveNopeWindow() {
    // 先 drain inbox 中积压的 Nope 消息
    g.drainPendingNopes()

    // 如果栈顶是 Nope，说明窗口内有人出 Nope，重新开启窗口
    if g.state.ActionStack.TopIsNope() {
        g.openNopeWindow(3 * time.Second)
        return
    }

    // 真的没人出 Nope，结算
    g.state.ActionStack.Resolve()
}

func (g *GameLoop) drainPendingNopes() {
    for {
        select {
        case msg := <-g.inbox:
            g.handleMessage(msg)
        default:
            return
        }
    }
}
```

### 多人同时出 Nope

所有消息通过 channel 串行化，不存在真正的"同时"。即使两个 WebSocket 读 goroutine 同时读到数据，它们写入 channel 时也是串行化的。游戏主 goroutine 从 channel 里一条一条读，自然有序。

## 5.3 各层职责说明

### Model 层（数据模型）

Model 层位于架构最底层，是一切领域逻辑的根基。它**不依赖任何其他层**，只包含纯数据结构和业务规则函数。

- 定义卡牌、牌库、手牌、玩家、游戏状态等核心实体
- 实现无副作用的纯函数：洗牌、抽牌、组合校验、Nope 链奇偶抵消
- 不包含任何 I/O 操作（无网络、无数据库、无文件读写）
- 不依赖任何外部框架或库（Go 标准库即可）

### Repository 层（数据持久化）

Repository 层对上层暴露接口，隐藏底层存储实现。Service 层只依赖接口，不依赖具体实现。

- 定义 Repository 接口，支持依赖注入
- 提供 Redis 实现：游戏状态快照的读写，设置 TTL 自动过期
- 提供 PostgreSQL 实现：用户信息、历史记录、排行榜的持久化
- 游戏进行中的热路径只走 Redis，游戏结束后才写入 PostgreSQL

### Service 层（业务编排）

Service 层是 Controller 和 Model 之间的桥梁，编排多个 Model 完成一个完整的业务流程。

- 游戏服务：协调 Deck、Hand、ActionStack 完成出牌→校验→执行→广播
- 房间服务：管理房间生命周期，协调玩家进出
- 回合服务：驱动 TurnEngine 完成回合流转，处理攻击叠加
- 超时服务：管理 TurnTimer、NopeTimer、ReconnectTimer 的生命周期

### Controller 层（请求处理）

Controller 层是外部请求的入口，负责解析输入、调用 Service、返回结果。

- 不包含业务逻辑，只做参数校验和请求分发
- HTTP Controller：处理 RESTful 接口（注册、登录、房间操作）
- WebSocket Controller：处理双向消息（出牌、抽牌、Nope、选目标）
- 将 WebSocket 的读 goroutine 与游戏主 goroutine 通过 channel 解耦

### View 层（序列化呈现）

View 层负责将服务端内部状态转换为客户端可见的格式，核心是"按视角过滤"。

- 每个玩家看到的游戏状态不同（自己的手牌 vs 对手的手牌数量）
- 序列化器根据玩家 ID 过滤敏感信息后生成 JSON
- 定义所有事件类型（state_update、nope_prompt、game_over 等）
- 定义统一的 HTTP 响应格式（code、message、data 结构）

## 5.4 请求处理流程

```
┌──────────┐     ┌────────────┐     ┌──────────┐     ┌──────────┐     ┌─────────┐
│  Client  │ ──> │ Controller │ ──> │ Service  │ ──> │  Model   │ ──> │  State  │
│ (WS/HTTP)│ <── │  (路由分发)  │ <── │ (业务编排)  │ <── │ (数据模型)  │ <── │ (变更)   │
└──────────┘     └────────────┘     └──────────┘     └──────────┘     └────┬────┘
                                                                          │
                                                    ┌─────────────────────┘
                                                    │
                                              ┌─────v─────┐     ┌───────────────┐
                                              │  View     │ ──> │   Client     │
                                              │ (序列化+广播) │     │  (按视角过滤)   │
                                              └───────────┘     └───────────────┘
```

### 完整流程示例：玩家出牌

1. **Client** 发送 WebSocket 消息 `{"type":"play_card","card_ids":["cat_01","cat_02","cat_03"],"target_player":"user_002"}`
2. **Controller**（game_controller.go）解析消息，校验 JSON 格式，提取参数
3. **Controller** 将消息放入房间 inbox channel
4. **Service**（game_service.go）从 inbox 读取消息，调用 Model 层的 MoveValidator 校验合法性
5. **Model**（hand.go → deck.go → action.go）执行出牌：从手牌移除、加入弃牌堆、入动作栈
6. **Service** 调用 TimerService 开启 Nope 等待窗口
7. **View**（serializer.go）遍历所有玩家，按各人视角序列化新状态
8. **Controller** 通过 WebSocket 将序列化后的状态分别发送给每个玩家
9. **Repository**（redis.go）异步将新状态快照写入 Redis

## 7.3 WebSocket 接口设计

### 连接建立

客户端通过 HTTP 升级建立 WebSocket 连接：

```
ws://<host>/ws?room_id={room_id}&token={token}
```

- room_id: 房间 ID（必填）
- token: 认证 Token（必填）

### 消息格式

所有 WebSocket 消息遵循统一的 JSON 格式。

**客户端 → 服务端（Request）**:

```json
{
  "type": "string",
  "payload": {},
  "req_id": "string"
}
```

| 字段 | 类型 | 必填 | 说明 |
|-|-|-|-|
| type | string | 是 | 消息类型标识 |
| payload | object | 是 | 消息体，内容随 type 变化 |
| req_id | string | 否 | 请求 ID，用于响应追踪 |

**服务端 → 客户端（Response）**:

```json
{
  "type": "string",
  "payload": {},
  "req_id": "string",
  "timestamp": 1712345678
}
```

| 字段 | 类型 | 必填 | 说明 |
|-|-|-|-|
| type | string | 是 | 事件类型标识 |
| payload | object | 是 | 事件体 |
| req_id | string | 否 | 对应请求的 ID（仅响应类消息） |
| timestamp | int64 | 是 | 服务端事件时间戳 |

## 7.5 接口安全设计

### 防篡改

- 所有涉及手牌操作的请求，服务端从自身状态中查询玩家手牌，**不信任客户端传入的 card_ids 增量信息**
- 客户端只能传 card_id，服务端在 Model 层校验该 card_id 是否确实属于该玩家的手牌
- 组合技校验（三张相同、五张不同）在服务端 Model 层重新执行，不信任客户端判定

### 防重放

- 每个 WebSocket 消息可携带 req_id，服务端检测重复 req_id 并丢弃
- 关键操作（出牌、抽牌）在服务端做幂等处理

- 广播时在 View 层按玩家视角过滤，确保每个玩家只能看到自己可见的信息
- 服务端代码中**不存在**"客户端请求对手手牌"的接口路径

按玩家视角过滤后发送，每个玩家看到的 state 不同。

| 字段 | 类型 | 可见性 | 说明 |
|-|-|-|-|
| YourHand | []Card | 仅自己 | 自己的手牌（完整信息） |
| Opponents | []PlayerDTO | 全员 | 对手信息（不含手牌详情） |
| DiscardPile | []Card | 全员 | 弃牌堆（公开） |
| DeckCount | int | 全员 | 牌库剩余张数 |
| DeckTopCards | []Card | 仅预言牌使用者 | 牌库顶牌（仅在使用预言后可见） |
| CurrentTurn | string | 全员 | 当前回合玩家 ID |
| PendingDraws | int | 全员 | 待抽牌数 |
| Phase | string | 全员 | 当前回合阶段 |
| ActionStack | []StackEntry | 全员 | 动作栈概览 |
| NopeRemainingMs | int | 全员 | Nope 窗口剩余毫秒 |
| GameStatus | string | 全员 | 游戏整体状态 |
| Direction | int | 全员 | 回合方向 |

```
Controller → Service → Repository (接口)
                  ↓
              Model (纯数据，零依赖)
```

- 依赖方向严格**从上到下**：Controller 依赖 Service，Service 依赖 Repository 接口和 Model
- Model 层**零依赖**，不导入任何 internal 包
- Repository 接口定义在 repository/interfaces.go，实现放在同包不同文件
- 所有依赖通过**构造函数注入**（NewXXX），不使用全局单例或 init()
